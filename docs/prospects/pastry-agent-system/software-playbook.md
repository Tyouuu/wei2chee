# 用 Claude 快速做出软件和 App

这是从 VIBE 456（一个月做出来、现在天天在用的真实记账系统）里提炼出来的做法。照着做，下一个软件会快很多，也少走很多弯路。

六大块：**做事的方法**（第 1 到 9 章）、**UI 手册**（U1 到 U8）、**功能手册**（F1 到 F10）、**App 篇**（A1 到 A4）、**上线之后**（O1 到 O5）、**管好 Claude 和检查员**（M1 到 M7），最后是一段开场提示。

## ★先记住这 7 句话（最重要）

1. **先把规则说清楚，再写代码。**规则写进一个文件（CLAUDE.md），每条写上「为什么」。
2. **先上线一个空壳，之后一小步一小步上线。**别攒一大堆再上线。
3. **钱和数据对不对，交给机器检查。**写自动测试，不靠眼睛看。
4. **设计先定一套规则**（一种卡片、三种按钮、几档字号），只改共用的地方，不改单个页面。
5. **凡是你会看到的改动，先出前后对比图。**你点头了才上线，不喜欢就保持现状。
6. **可以让很多个 Claude 同时做事，**但每个只管一块、互不重叠，一块一块上线。
7. **上线成功不等于做好了。**上线后一定在线上真的量一遍、走一遍。

## 1开工前：先写一页「业务一页纸」

用自己的话，回答 5 个问题。写不清楚的地方，就是以后最容易出错、最容易返工的地方。

- **谁在用？**几个人，各是什么角色。
- **一天怎么用？**最常做的 3 件事，一步一步写出来。
- **钱和数据怎么算？**收入、成本、数量，每个数字从哪来。
- **什么绝对不能错？**比如：不能卖超过库存、已结账的月份不能改。
- **什么现在不做？**写下来，Claude 就不会自己加功能。

VIBE 456 的例子

一个老板签字；只有两种收入（点数的 2%、每张卡 RM 1.50）；经销商不赊账；更正不改原记录。这些写进 CLAUDE.md 以后，Claude 再也没有提过「欠款管理」「双人审批」这类用不上的功能。

**已经决定的事也要记下来，写上原因。**这样下次不会重复问你，也不会被改回去。

## 2技术选择：选省心的组合

- **网页：Next.js；数据库、登录、权限：Supabase；自动上线：Vercel。**都是托管的，不用自己管服务器。推到 GitHub 就自动上线。
- **权限放在数据库里**（行级权限），不能只靠页面把按钮藏起来。
- **钱用「账本」的做法：**只能加，不能改、不能删。要更正，就加一条新记录指向旧的，页面上合并显示成一行「改过 N 次」。结账之后整个月锁定。
- **手机和电脑一起做。**不要因为你说的是「网站」就只做电脑；一开始就两面一起规划。
- **能用现成的就用现成的。**登录、邮件、推送、读图片都接现成服务，别自己写。

## 3让 Claude 变成靠谱搭档

### CLAUDE.md：项目的大脑

放规则、设计系统、禁区、已定的决定、踩过的坑。每做完一件事就更新一小段。越具体越好用，比如「每屏最多一个深色按钮」，比「界面要简洁」有用一百倍。

### 记忆文件：你纠正过的事，永远记住

每次你说「不是这样」，就记一条：发生了什么、为什么、以后怎么做。VIBE 456 里有七十多条，所以后来同样的错越来越少。

### 说话和做事的规矩

- 用你的语言、简单的词。先说结论，再说细节。
- **做之前先用一句话复述范围。**你没提到的，不改、不加。「做真数据」不等于「可以多加一块」。
- 样子、范围这类需要你拍板的事，先给选项和预览，不要自己猜。猜错一次，要白做一整轮。
- 界面里**同一个东西只用一个词**。所有界面用词放在固定的几个文件里，再写一个测试守住（VIBE 456 里「待发货 / 已发货」「收据」都是这样定下来的）。
- 要你自己的账号才能做的事，才请你做；能自己做的，Claude 自己做。

## 4质量靠机器守，不靠眼睛

**6,900+**个自动检查，每次约 1 分钟跑完

**450+**个测试文件

**100+**项修复，一天内分块上线

### 测试分 5 层

1. **金额和规则的小函数：**最先写，最便宜，最重要。
2. **页面渲染：**把页面画成静态内容，检查该有的字、该有的数字在不在。
3. **规则测试：**让测试去读源代码，守住设计规则。例如「每屏最多一个深色按钮」「字号只能这几档」「一个概念一个词」。这样以后谁改都不会悄悄破坏。
4. **数据库测试：**直接测数据库里的规则（防超卖、防重复、锁月）。
5. **端到端：**用真浏览器把整个流程点一遍。

**每次上线前：**类型检查、代码检查、全部测试，必须一次全过。不是「大部分过」。

### 用真浏览器量一量

- 用 Playwright 在真实的手机和电脑窗口里量：尺寸、对齐、有没有溢出、手指能不能点到（至少 44 像素）。
- **在线上量，用「只读模式」：**脚本里把所有写入请求拦住，放心在真数据上量。
- 量过之后写成固定脚本，以后每次上线都能再量一遍。

### 把整个流程用真数据走一遍

测试看不到的问题，靠「走查」：新增商户 → 他提交申请 → 你接受 → 发货 → 月账。看每一步数字有没有跟着动、下一步有没有出现。

### 数据正确的几条硬办法

- 金额用数据库一次汇总，**不要在页面里把拿到的行加起来**（接口默认只给 1000 行，会悄悄少算）。
- 防重复：给文件算指纹，同一张收据、同一个参考号第二次就拒绝。
- 防超卖：库存够不够，在数据库里硬检查，页面只负责提示。
- 用「第二种算法」对一遍账：同一个数，用另一条路径再算一次，对不上就是有错。

## 5设计：快、好看、统一

- **先定设计系统，再做页面。**一种卡片、三种按钮（深色主按钮每屏最多一个；白底细边的；纯文字的）、固定几档字号、一种「选中」的样子。
- **只改共用的地方。**某一页觉得不好看，不要单独改那一页，去改它用的那个共用部件，所有页面一起变好。
- 原则四条：**同一功能同一个样子；一件事只说一次；不需要的直接删，不要折叠藏起来；少，就是高级。**
- **动效也写成全局规则：**只动透明度和位移，不超过 0.4 秒，尊重手机上的「减弱动态效果」。
- **页面打开先出灰色骨架，**大小和真页面一样，内容出来时不跳。
- 你自己画的页面要尊重，别擅自改。想改，先出前后对比图。
- 觉得「不够好」的时候，先查**数据和结构**有没有错，往往不是样式的问题。

## 6协作节奏：最省时间的部分

- **一块一块来。**每一块先出前后对比页（真截图，每项有编号），你只要回「上线」「保持现状」或者几号。没提到的，就保持现状。
- **多个 Claude 并行：**每个只管一块，文件尽量不重叠；每个都说清楚「先量后改」「不要碰什么」。VIBE 456 一天里用七个同时做，改了一百多项。
- **大改动用独立的副本（git worktree）：**每一块在自己的副本里做、测、提交，这样每一块都能单独上线，也能单独退回。
- **汇报的格式：**先结论；然后三样：做了什么、没做什么、要你决定什么。用简单的话，不堆术语。
- **估时间给范围，并说明前提。**不确定就直说不确定，别乐观。
- 先出 demo 的好处：你不喜欢，就不用做那么多测试和整理。喜欢了再认真收尾上线。

## 7上线流程（别踩坑）

1. **数据库改动先在演示库试一遍**（最后总是回滚），确认没问题再正式执行。**先改数据库，再推代码。**
2. 推送代码，等自动部署变成「成功」。部署失败时，线上还是旧版，不会坏，但要去看原因。
3. **然后在线上真的验证：**线上的样式文件里有没有新东西；用真账号只读地走关键页面，量几个数。「成功」不等于做好了。VIBE 456 有一次页面是新的、样式还是旧的，原因是构建缓存。以后每次推送后都要验证。
4. **备份：**自动备份，再加一份离开这台电脑的。密钥不进代码仓库，仓库设成私有。
5. **在线上造测试数据：**只用专门的测试商户，通过真界面提交，名字带 QA 标记，用完好清。

## 8Windows + OneDrive 的坑

| 问题 | 怎么办 |
| --- | --- |
| 在 OneDrive 文件夹里跑开发服务器会崩或一直卡住 | 用「先构建再启动」；开发和预览放在 OneDrive 外面的文件夹 |
| 电脑会断线，对话中断，后台任务跟着没了 | 重要进度写进文件；构建和预览服务用独立的后台进程启动 |
| 通过「链接文件夹」删除，会把真文件一起删掉 | 删链接只用 rmdir；删之前先看清楚它指向哪里 |
| 命令行里拼多行文字，反斜杠被吃掉 | 写文件用编辑工具；换行符一律 LF |
| 字体下载偶尔失败导致构建失败 | 构建脚本自动重试几次 |
| 改了样式，线上还是旧的 | 在 Vercel 里设「不用构建缓存」，并在每次上线后检查线上样式 |

## 9新项目 10 步清单（可以直接照做）

1. 写「业务一页纸」（第 1 章的 5 个问题）。
2. 建代码仓库，写 CLAUDE.md：规则 + 为什么 + 禁区。
3. **先把空壳上线。**以后每一步都是在线上的东西上改。
4. 数据库设计 + 权限 + 账本规则。
5. 先做最重要的一条完整流程：从输入，到报表，一刀切到底。
6. 金额的小函数先写测试。
7. 设计系统先于页面。
8. 每个功能：复述范围 → 做 → 测 → 线上核对。
9. 每周一次全面量：对齐、用词、功能走查。
10. 每次被纠正，都记进记忆文件。

## UI 手册：又快又好看，还统一

下面的数字是 VIBE 456 真正在用的。做新项目时，先照抄，再按它的样子微调。

## U1先定「手感」：用三个词决定整体样子

VIBE 456 的三个词是：**轻、静、整齐。**轻，是按钮和块不厚重；静，是颜色少、装饰少、只有一个主色；整齐，是所有东西用同一套尺寸。

把你的三个词写进 CLAUDE.md。以后每个取舍都问自己：轻不轻？静不静？齐不齐？答不上来的，就删掉。

觉得「高级」，几乎都是做减法得来的：去掉一个框、一种颜色、一句多余的话，页面反而更好看。

## U2设计系统：一页数字，写死

| 项目 | 规则（手机） | 为什么 |
| --- | --- | --- |
| 字号 | 只用 12 / 14 / 16 / 20 / 30 五档；粗细只用 400 / 500 / 600 | 档越少，页面越整齐 |
| 间距 | 页面左右边距 16；块与块之间 12；列表里卡片之间 10；标题到下面的内容 8 | 间距只有几个数，页面才有节奏 |
| 能点的东西 | 高度至少 44 像素（标签、按钮、行、小链接都算） | 手指比鼠标粗 |
| 卡片 | 白底、大圆角、很淡的边和影子；页面底色是淡蓝灰 | 轻 |
| 按钮 | 三种：深色实心（每屏最多一个，只给「下一步」）；白底细边；纯文字 | 让人一眼知道该按哪个 |
| 颜色 | 一套偏蓝的深灰中性色 + 一个主色；状态用「小圆点 + 一个字」，不用大色块 | 静 |
| 选中的样子 | 白底（标签用白色滑块）或白底深色细边，不用实心黑 | 黑色只留给「要按的按钮」 |
| 数字 | 金额靠右对齐；「RM」小字 + 整个数字同一个大小；今年的日期不写年 | 一眼能对比 |
| 动效 | 按下缩到 97% 再略变暗，0.12 秒；窗口升起 0.24 秒；全部不超过 0.4 秒，只动透明度和位移 | 流畅又不抢戏 |

电脑版的数字不一样，但道理相同：卡片内边距 24，表格行高只有 56 和 72 两种，按钮和输入框一样高（40），行里的小按钮一样高（30）。

## U3页面怎么拼：只用几种「积木」

- **一条记录 = 一张卡：**名字、金额、一行小字、「查看详情 ›」。所有列表用同一张卡，只在一个地方改它。
- **一天一个日期标题，卡片分开放。**不要把一堆记录装进一个大白框。
- **表格：**最后一列靠右、文字和数字一直排到表格右边；行高只有两种；操作列顺序固定（先「更正」，后「查看详情」）。
- **窗口：**从下面升起，顶上有一条小横条；底部永远是「取消（文字）+ 保存（深色）」；窗口开着的时候，后面的页面不能滚。
- **底部栏：**每页最多一个；离内容的距离固定，内容滑到底不被挡住。
- **标签条：**选中的用白色滑块；数字只写在「有事等你处理」的标签上，不写「一共有多少」。
- **每种页面都要有三个状态：**空的、加载中（灰色骨架，大小和真页面一样）、出错了。

## U4做 UI 的流程：一页一页，有人拍板

1. **先照着做：**老板画页面或给参考，Claude 照着做，不加不减。
2. **再做减法：**去掉没用的字、框、说明。「删掉」比「折叠起来」好。
3. **最后接真数据：**用真数据看，并且看三种情况：空的、很多的、名字很长的。
4. **每一步都出前后对比图**（真截图），你说行才往下走。

- 新的功能页面，先说清楚三件事：**哪一页、什么功能、给谁用**，再画。
- 觉得「不够好」的时候，先查**数据和结构**是不是错了（比如数字少算、顺序不对），样式放在最后。
- 像资深设计师那样看：找出「廉价的、过时的、不整齐的」地方。真正高级的页面，是有克制的。
- 避开「一看就是 AI 做的」样子：满屏渐变、到处圆角、到处图标、到处彩色标签。

## U5把「好看」量出来，别只靠感觉

用真浏览器（iPhone 用的那个引擎）去量，量这些：

- 左右边距是不是都一样；块与块之间的间距是不是只有那几个数。
- 金额的右边有没有排在一条线上；同一行里名字和金额的基线对不对。
- 有没有字被切掉、有没有叠在一起、有没有横向滚动、手指能不能点到。
- **同一种东西，在不同页面里大小要一样：**按钮高度、卡片内边距、标题位置、「查看详情」的位置。把它们逐页对一遍。
- 窄屏（320）、宽屏（430）、中文、英文都要看。英文通常更长，最容易挤爆。
- 量完写成脚本，以后每次上线再量一遍。VIBE 456 靠这个一次就找出了三十多处不整齐。

## U6手机特有的坑

- 窗口打开时，锁住后面的页面；键盘弹出来，不能挡住「保存」。
- 底部栏要避开 iPhone 底部的横条。
- 装到主屏幕以后，状态栏的颜色要和页面底色一样，不然顶上会有一条不搭的色带。
- **手指一按就要有反应：**点标签，滑块立刻动，内容随后到；等的时候先出灰色骨架，不要干等。
- **长列表：**一次读 20 条，滑到底自动接着读，不设上限，提前读好下一屏。
- 日期、选择都用自己画的窗口，不用系统自带的灰色弹窗，风格才统一。
- 真的要在真手机上试一次：滑动的手感、键盘、分享菜单，模拟器看不出来。

## U7手机和电脑一起做

- 同一个页面，两边的**字、顺序、数字**要一致。电脑多出来的是「更宽」，不是「更多」。
- 电脑版的整体框架固定：左边栏宽度、页面标题的位置、内容的左边，每一页都一样。
- 窗口宽度和底部按钮的样子，两边用同一种。
- 量的时候，电脑版要看 1440、1280、1024 三种宽度，窄了表格不能丢列。

## U8文字也是 UI

- **用简单的词。**老板看不懂「水单」，就全部改成「收据」，一处不留。
- **一个东西一个名字，**所有界面用词放在固定几个文件里，再用测试守住。
- 中文和英文要意思对得上，不能一个说「申请」一个说「订单」。
- **提示的写法：**说发生了什么，再说怎么办；不道歉，不说术语。
- **一件事只说一次。**说明文字能删就删，只留下「会影响决定」的警告。

## 功能手册：做得对，才不会出错

做记账、库存、订单这类系统，功能的重点不是「多」，而是「每个数字都对，每一步都能追查」。

## F1先画「状态和流程」，再写功能

- 把一件事从头到尾的状态画出来。VIBE 456 的一条线是：经销商提交申请 → 已接受 → 待发货 → 已发货 → 记快递费 → 月账 → 和上游的账单对账。
- 每个状态都回答三个问题：**谁能看？谁能改？改了会影响哪些数字？**
- 每个数字问一句：它是「存起来的」还是「算出来的」？**能算出来的就别存，**少一个存的地方，就少一处可能出错。

## F2钱和数据的规则（最值钱的一部分）

- **账本只增不改。**更正是一条新记录，指向被更正的那条，页面上合并显示；更正算进原记录所在的月；结账之后整个月锁定。
- **数字尽量用整数。**点数不出现小数；金额固定两位小数。
- **汇总只在数据库里算。**页面不把拿到的行加起来。每个数字只有一个算法，所有页面都用同一个（「说一次」）。
- **防重复：**文件算指纹，同一张收据第二次就拒绝；参考号重复就拒绝；提交带一个唯一键，手滑按两次也只算一次；每个链接每小时有次数上限。
- **防超卖、防透支：**数据库里硬检查，页面只负责提前提示。
- **对账：**用第二种算法再算一遍，对不上就是有错；每晚自动「系统自检」（VIBE 456 有 15 条规则），自动发现数字对不上。

## F3权限：少而清楚，放在数据库里

- 角色要少而清楚（VIBE 456 只有三个）。**权限放在数据库那一层：**某个角色看不到钱，就连接口都拿不到，不是只把页面藏起来。
- **一个人拍板。**不要为了「看起来专业」加用不上的审批流程；真实的业务里只有一个人签字，就只做一个人签字。
- **外面的人不进系统：**给经销商一个专属链接，他只能提交申请；申请先进「待处理」，员工接受以后才进账本。

## F4每个功能的 11 条检查清单

开发前对一遍，上线前再对一遍：

1. 谁能用？（角色）
2. 输入怎么校验？（金额、倍数、必填、上限）
3. 重复提交怎么办？
4. 出错了怎么提示？（说怎么办）
5. 做错了怎么更正？（必须有更正的路，不能改原记录）
6. 会影响哪些数字和报表？
7. 要不要通知？（推送、邮件）
8. 要不要记操作记录？
9. 手机和电脑都有吗？
10. 空的、很多的、很慢的时候什么样？
11. 测试了吗？（规则测试 + 一条完整流程）

## F5后台任务和通知

- **定时任务用数据库自己的定时器。**平台自带的免费定时器会晚到一个小时；VIBE 456 的「每晚 9 点日报」用数据库定时，按分钟准时。
- **手机推送：**只推「要你处理」的事（新的待处理申请、新订单）。做好以后，一定在真手机上收一次。
- **邮件：**接现成的邮件服务，发信域名要先验证，不然会进垃圾箱。

## F6让机器读图片或文件（识别）

- 让机器读收据，省得手动打字。但**读出来的数字要给人确认，**并且和申请里填的金额对一下，不一样就提示。
- **选模型：**用你自己的真实样本做一次对比，选准确又便宜的；不凭名气。
- 读不出来、读错了，都要有「改成手填」的路。

## F7导入和导出

- **导出：**老板要看的东西，放进一个文件、一张表（VIBE 456 的 Excel 就是一个文件一张「商户」表，打开就看到收入）。样式定好以后不要再变。
- **导入：**先预览，再确认；重复的跳过；导入也要有记录。

## F8数据库改动和备份

- 每次改动是一个**带编号的小文件**，一次只做一件事。
- 先在演示库试一遍，写成「最后总是回滚」的试跑，确认没问题再正式执行；**先改数据库，再推代码。**
- 备份要自动、要频繁（VIBE 456 每 5 分钟一次），而且要有一份离开这台电脑；定期想一想「备份在不在、能不能恢复」。

## F9怎么证明功能是对的

- 先给**规则**写测试（金额怎么算、什么时候拒绝）。
- 再写**走一遍整个流程**的测试，从新增商户到月账。
- 上线以后，用测试商户**通过真界面真的提交一次**，看数字有没有跟着动。
- 让「系统自检」每晚自己查。出问题它会先告诉你，不用等客户发现。

## F10「故意不做」也是功能

把不做的东西和原因写下来，Claude 就不会反复提：

- 经销商不赊账，所以不做欠款和信用额度。
- 只有一个人签字，所以不做双人审批。
- 收入只有两种，所以不做别的奖励计算。
- 没有包裹这个东西，只有「订单」。

每次想加功能前先问：**这是老板真的在用的吗？**不是，就别加。

## App 篇：怎么变成手机里的 App

做软件的人最容易想太重：一上来就做原生 App、上应用商店。VIBE 456 的做法轻得多，也快得多。

## A1先做网页应用，别急着上应用商店

- **一套代码，手机和电脑都能用。**网页做成「可以装到主屏幕的应用」（PWA）：有自己的图标，打开是全屏，看起来和 App 一样。
- 应用商店要付费、要审核、每次更新都要等，一个小团队前期不值得。等设计定稿、真的需要了再包一层。
- **手机优先来设计：**先在手机上做对，电脑版是「更宽」。

## A2让它「像 App」要做的几件事

- **应用说明文件（manifest）：**名字、图标（192 和 512 两种尺寸，再加一个适合圆形裁切的）、全屏显示、起始页。
- **状态栏颜色和页面底色一样。**否则装到安卓以后，顶上会有一条不搭的色带（VIBE 456 就修过这个）。
- **躲开手机的刘海和底部横条，**页面最底下的按钮不被盖住。
- 不做离线功能就别硬做；记账系统要的是「永远是最新的数字」。
- 在 iPhone 上，用户要自己点「分享 → 添加到主屏幕」。把这三步写在「我的账户」页里，别指望用户自己找。

## A3推送通知

- 网页也能给手机发推送（Web Push）。**iPhone 要先把应用添加到主屏幕，才收得到。**
- 只推「要你处理」的事（新的待处理申请、新订单），别推「一共有多少」。推多了，用户会全关掉。
- 做好以后，**一定在真手机上收一次**，模拟器收不到。

## A4外面的人用「链接」，不用装 App

- 经销商这类外面的人，给他一个**专属链接**（微信、WhatsApp 发过去），打开就能提交申请，不用装任何东西、不用注册。
- 链接里的页面要最简单：一屏填完，字大，支持中英文。
- 要给自己人装「安卓安装包」，等界面都定稿了再包一层，直接把文件发给他们；iPhone 继续用「添加到主屏幕」。

## 上线之后：安全、监控、备份、速度

做出来只是一半。系统每天都在用的时候，要保证它不出事，出事能马上知道、能救回来。

## O1安全清单（小团队也要做到的）

- **代码仓库设成私有。**备份文件、密钥都不能放进公开的地方（VIBE 456 就发现过备份曾经是公开的，马上改成了私有）。
- **密钥只放在服务器的环境变量里。**不进代码；泄露过就换。
- **权限放在数据库那一层，**不靠页面藏按钮。
- **限流：**公开的提交入口，每个链接每小时有次数上限，防止被人刷。
- **登录：**闲置一段时间自动退出；跳转地址要检查，防止被带到别的网站。
- 每隔一段时间，让 Claude 专门做一次「安全检查」，把发现的写成清单逐条改。

## O2监控：出事你要比客户先知道

- 一个**健康检查地址**（打开就返回「正常」），再接一个定时探测的服务，挂了发邮件。
- **报错收集：**页面和服务器里的报错，自动收集到一个地方。
- **每晚自检：**自动对数字、查异常（第 F2 章），结果发给你。
- 重点是「出事会通知我」，而不是「我天天去看」。

## O3备份：定期确认它真的在跑

- 自动、频繁、而且**有一份离开这台电脑。**
- **免费额度用完，备份任务会悄悄停掉。**VIBE 456 就发生过：云端的每晚备份因为额度用完，停了好几天，没有人发现。备份任务要自己报告「我成功了」，失败了要发提醒。
- 每隔一段时间，真的做一次「恢复演练」，确认备份能用。

## O4费用和限额

- 托管服务的免费版都有上限（构建时间、数据库大小、定时任务次数、自动化的分钟数）。上线前把上限列一张表，每月看一眼。
- 定时任务不准时、构建被限速、备份停了，都先怀疑是不是额度到了。

## O5速度：量，不要猜

- **服务器和数据库放在同一个地区。**VIBE 456 的页面一度很慢，原因是服务器在美国、数据库在新加坡；改成同一个地区就好了。
- 列表一次读 20 条，滑到底再读下一页；打开先出骨架。
- 觉得「变慢了」时，**用同一个办法量不同版本**（点标签到页面出来，各个版本各量几次），再下结论。VIBE 456 量出来：现在和前三个版本一样快，慢的感觉来自「等的时候什么都不动」，所以改的是等待时的样子。
- 一个页面要读好几样数据时，让它们同时读，不要一样一样等。

## 管好 Claude 和检查员

你不是在「使用」Claude，是在「管」一个很快、很勤奋、但会出错的团队。这一块的规矩，决定了你省多少时间。

## M1它说的是「说法」，不是「事实」

- 检查员说「没问题」，只代表它这么认为。**要数字、要截图、要文件位置，**然后自己抽查几个。
- 最好的验证是**上线后在线上量**：同一个脚本，对线上跑一遍，看数字。
- VIBE 456 就出过：部署显示成功，页面却是旧样式；我曾说「没有备份」，查了才知道有。**没查之前，不说「没有」「正常」「做完了」。**

## M2给检查员的任务要写清楚

- 写明：**范围**（只管哪一块）、**不能碰什么**、**怎么交差**（数字、截图、改了哪些文件、测试结果）。
- 说清楚「先量后改」，别让它凭感觉改。
- 让它先把「改之前」的样子拍下来，再改。以后做前后对比就有了。

## M3并行不打架的规矩

- 每个人管的文件尽量不重叠。
- 大家都要改的共用文件（样式、说明文件、测试），只做**小改动，改之前先重读**。
- **大改动用独立副本**（git worktree）：每一块能单独测、单独上线、单独退回。
- 不要同时构建（共用的缓存会打架）；预览用不同端口，或者一个一个来。

## M4记下「谁负责什么」

同时叫起好几个检查员时，**马上写下「编号 → 任务」**。VIBE 456 出过一次：把两个检查员的编号弄反了，给每个发了对方的指示。检查员中断了，可以发消息让它接着做，做过的都不会丢（前提是它把东西写在文件里）。

## M5长对话会被压缩：把「做到哪」写下来

- 对话太长，Claude 会把前面的内容压缩，细节会丢。
- 重要的决定、现在做到哪、下一步，**写进记忆文件和说明文件。**电脑断线、对话重开，也能接着做。
- 后台任务别绑在对话上：用独立进程，把进度写进文件。

## M6出问题先量，不猜

1. **先复现：**在同样的条件下，再做一次，看是不是真的。
2. **先量：**把数字量出来（时间、大小、位置），不要说「好像」。
3. **二分法：**是哪一次上线开始的？把不同版本都量一遍，找到分界点。
4. **先怀疑缓存，再怀疑代码：**样式不对、数字不更新，十次有八次是缓存。
5. 改完以后，**用同样的办法再量一次**，证明真的好了。

## M7不确定就说不确定；错了马上更正

- 估时间给一个范围，说明前提；不确定就直说。
- 说错了，立刻更正，并且写进记忆文件。这是让团队越来越靠谱的办法。
- 不要把自己做不了、需要用户账号的事，推给用户；能自己做的自己做。

## 10开场提示：复制到新项目的 CLAUDE.md 开头

新项目第一天，把下面这段话放到 CLAUDE.md 最前面，再接着写你自己的业务规则。

```
你是我的软件搭档。我只看中文，请用简单的中文跟我说话，先说结论。

工作方式：
1. 开始做之前，先用一句话复述你理解的范围。我没提到的，不要加。
2. 样子、范围这类需要我决定的事，先给选项和预览，不要自己猜。
3. 凡是我会看到的改动，先做前后对比（真截图、有编号），我说「上线」才上线。
4. 钱和数据：只增不改，更正是新记录；金额用数据库汇总，不在页面里累加；权限放在数据库里。
5. 每次改动：类型检查、代码检查、全部测试都必须通过；上线后在线上真的核对一遍。
6. 一个概念只用一个词；界面里的词放在固定的几个文件里，用测试守住。
7. 设计系统：一种卡片、三种按钮（深色主按钮每屏最多一个）、固定几档字号；只改共用的地方，不改单页。
8. 我纠正过的事，记进记忆文件（发生了什么、为什么、以后怎么做）。
9. 可以多个助手并行，但每个只管一块、文件不重叠，大改动用独立副本，一块一块上线。
10. 汇报：做了什么 / 没做什么 / 要我决定什么。
```
