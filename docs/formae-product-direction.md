# Formae 产品方向：让"客户自己设计系统"真正成立

写于 2026-08-20。起因：portal + 编辑器上线后 founder 亲自试用，判断"半桶水"，
并要求想清楚"怎么才能完美结合我最初的想法，做到我真正想要的 AI SaaS"。

本文档是**方向性设计**，不是实施计划。实施计划另开。
已知问题清单见 `docs/portal-editor-known-issues.md`。

---

## 一、最初的想法（不能走偏的那条线）

founder 原话：
> 客户可以参与进来自己的 system 设计，我负责根据他们的想法/设计做出一份他们想要的 system。
> 市场上我没有看到这个 concept，所以我希望可以借助这样的 concept 去拿到更多客户。
> 论经验我又赢不到他们，论作品数我又赢不到他们，所以这个 AI SaaS 一定要弄得很好看、很好用，不能弄得半桶水。

拆解出三个不可动摇的点：
1. **客户要"参与设计"** —— 不是看方案，是亲手改
2. **创办人负责真正落地** —— 客户设计的是"想要什么样"，不是最终产品本身
3. **靠 concept 取胜，不靠价格/资历** —— 所以体验必须完整，半成品反而伤害说服力

对手 XYSTEM 的模式：讲需求 → 报价 → 黑箱开发 → 验收。
**客户在付钱前，永远看不到东西。** 这就是我们要打的点。

---

## 二、真正的断裂：AI 的理解被丢掉了

现在的流程：

```
获客站                          │ portal
选行业 → 答问卷 → AI 分析报告    │ 注册 → 盲选风格 → ⬛ 空白画布 → 自己拖方块
        ↑                       │                    ↑
   AI 在这里懂了客户              │              这里全部忘光
```

`industries` 表里 AI 已经按行业算出该开哪些模块（餐饮只要 2 个、装修要 4 个），
但 migration 写死了每个客户一律开 5 个页面（dashboard/customers/quotations/projects/payments）。
**分析结果从来没有被用过。**

结果就是：客户在获客站被"你懂我"打动，进来后面对一张空白画布，
体验从"这是为我做的"跌回"这是个通用工具"。

**这一刀不接上，做再多组件、再多主题都是在补皮肤。**

---

## 三、核心设计：AI 的产出 = 客户的系统雏形

一句话概括方向：

> **AI 分析的产出，不应该是一份客户读完就走的报告，
> 而应该直接变成客户可以动手改的系统雏形。**

客户注册后打开编辑器，看到的**不是空白画布**，而是一套已经按他的行业、
他的问卷答案摆好的系统 —— 然后他在这个基础上改。

- 餐厅老板打开 → 已经有桌台状态板、今日订单、常客名单
- 装修老板打开 → 已经有工地进度、材料报价单、收款记录

他做的事从"从零开始搭"变成"这个不要、那个改个名字、颜色换一下"——
**门槛从"会用设计工具"降到"会表达意见"**，而这正是中小商家老板能做到的事。

### 为什么这一条能同时解决多个问题

| 原有问题 | 如何被解决 |
| --- | --- |
| 空白画布吓人（问题 #1） | 画布永远不空，打开即有内容 |
| 感受不到"在设计一整个系统"（问题 #6） | 一进来就是完整系统，不是一个页面 |
| 行业差异化不存在 | 模板本身就是行业差异化的载体 |
| AI 分析结果被浪费 | 分析结果成为雏形的输入 |
| 组件太少/太抽象 | 客户不需要认识组件，模板已经摆好了 |
| 风格盲选不可逆（问题 #7） | 模板自带推荐风格，可随时切换预览 |

## 四、技术上怎么做（不需要新技术）

### 4.1 行业模板库 ≠ AI 实时生成布局

两种做法：

- ❌ **AI 实时生成 Puck JSON**：慢、质量不可控、每次结果不一样，翻车风险高
- ✅ **人工设计的行业模板 + AI 做填充/裁剪**：质量可控（模板是精心设计过的）、
  秒开、仍然个性化

**这也是 Durable / B12 的真实做法** —— 他们不是从零生成，是有模板库，
AI 负责挑选和填内容。我们之前误以为他们在"实时生成"。

### 4.2 一个行业模板包含什么

```
industry_templates/
  fnb.json          餐饮
    ├─ pages[]              该行业该开哪些页（不再一律 5 个）
    ├─ layout per page      每页的 Puck JSON（用现有 21 个组件拼）
    ├─ sample data          行业术语的示例数据（"3号桌""外卖单"）
    └─ recommended style    推荐风格
  renovation.json   装修
  beauty.json       美容
  ...
```

模板就是**一份 Puck JSON**，用的是我们**已经做好的 21 个组件**
（`data-grid` 真表格、`rail-nav` 侧边栏、`filter-chips`、`date-picker`、
`receipt-field` 等），不需要新组件、不需要新架构。

### 4.3 AI 在其中做什么（这才是"AI SaaS"）

AI 目前只出现在获客站一次，产出一份被丢掉的报告。应该出现在三处：

| 阶段 | AI 做什么 | 客户感受 |
| --- | --- | --- |
| **① 生成雏形** | 读行业 + 问卷 → 选模板、裁剪模块、填入客户自己的业务术语 | "它真的懂我的生意" |
| **② 对话式修改** | 客户不会拖拽也没关系："我要加个记录客人生日的地方" → AI 改布局 | "我不用学工具也能改" |
| **③ 生成需求书** | 把最终设计翻译成给创办人的系统规格文档 | "我付的钱有实实在在的东西" |

**② 是把"拖拽工具"变成"AI SaaS"的关键。** 中小商家老板不一定会用拖拽编辑器，
但一定会用嘴讲。Framer / Durable 都在往"对话 + 可视编辑并存"走，方向一致。

### 4.4 交付环节（③）为什么重要

现在的 Deploy 是一条 WhatsApp 消息 + 一个 layout_json。这对创办人来说不够用，
对客户来说也感受不到价值。

应该由 AI 生成一份**系统需求书**：行业 + 问卷答案 + AI 分析 + 客户最终设计
+ 客户改过的字段名 → 一份专业规格文档。

- 对客户：付 RM5000 前看到一份正式文档，物有所值
- 对创办人：拿到的是可直接照着做的规格，不是猜客户想要什么
- 对差异化：XYSTEM 的客户在付钱前只有一张报价单

## 六、建议的推进顺序

按"最小投入换最大客户感知"排：

**第一步：让画布不再空白（复用为主，几乎零新设计）**
1. 把 16 个已做好的组件注册进编辑器（含 `data-grid`、`rail-nav`）
2. 手工做 2–3 个行业模板（先做 founder 最熟的行业）
3. 注册时按行业开页面，不再一律 5 个
4. 用 `rail-nav` 补上页面导航

做完这一步，客户打开看到的就是"我的系统"，而不是空白框。
**这一步本身就足以让 concept 立起来。**

**第二步：行业与风格真正对齐**
5. 从 21st.dev 主题库扩风格，命名对齐数据库里的 6 个行业推荐
6. 风格改成可随时切换 + 实时预览（去掉"不可逆盲选"）
7. 补齐其余行业模板

**第三步：把 AI 真正接进来**
8. AI 从问卷答案自动挑模板 + 填业务术语（获客站 → portal 打通）
9. 对话式修改（"帮我加一个…"）
10. AI 生成系统需求书，作为 Deploy 的真实产出

**第四步：落地页构建器**（原 Phase 2，不变）
同一个编辑器多注册一批营销组件，复用获客站已有的 hero/动效素材。

## 八、开发流程必须改：审查的单位是"客户的一次完整旅程"

founder 的判断（2026-08-20）：
> 不能每一个单独 review，因为每一个单独 review 的话，都发现不到结合的问题。
> 我要的完整的 AI SaaS，不是每一个都是分开的。

这个诊断是对的，而且不是"审查不够仔细"的问题 —— 是**审查的单位选错了**，
再仔细也发现不了。

### 8.1 为什么单任务审查结构性地看不到这些问题

本次计划 9 个任务全部通过独立审查、最后还做了一次全分支审查，仍然漏掉了
产品最严重的几个问题。原因不是疏忽，是每一类问题都落在审查范围之外：

| 漏掉的问题 | 为什么单任务 review 不可能发现 |
| --- | --- |
| AI 分析结果在注册时被丢弃 | 这是**缺失**不是改动，diff 里没有任何一行是错的 |
| 数据库 6 个行业风格 vs 实际做的 3 个 | 横跨**两个不同计划**（获客站 / portal），任一计划的审查只看得到一半 |
| 21 个组件只注册了 5 个 | 每个组件当初都通过了审查，"没被接进去"不属于任何一个任务 |
| 空白画布是客户的第一眼 | diff 无法表达"第一眼的感觉"；所有测试都是"拖一个组件进去"才开始看 |
| 编辑器像默认 Puck 换色 | 每一步换色都正确，"整体像不像一个产品"从来不是任何一步的验收标准 |

连最后的全分支审查也只挡下一部分 —— 因为它审的仍然是**本计划的 diff**，
而获客站属于**另一个计划**。**计划与计划之间的接缝，不归任何人负责。**

每个计划内部都自洽，产品是它们的并集，而这个并集是没有主人的。

### 8.2 硬规矩

**规矩一：每个计划开工前，先画出它在完整客户旅程中的位置。**
明确写出上游接口（从哪继承数据/状态/客户认知）和下游接口（交给谁、交什么）。
接缝必须有明确的归属，不能默认"下一个计划会处理"。

**规矩二：每个任务必须声明"我消费什么、我产出什么"。**
不只是文件层面的输入输出，包括**客户认知层面**的：
上一步客户以为会发生什么？这一步有没有辜负它？

**规矩三：新增一类审查 —— 旅程审查（Journey Review）。**
- 单位不是 diff，不是任务，是**一个真实客户从头走到尾的完整旅程**
- 方式：扮演一个具体的人（例："餐厅老板阿明"），从第一次打开网站，
  一路走到最终交付，**每一步截真实的图**
- 专门找的不是 bug，是**断裂**：
  - 上一步建立的期待，下一步有没有兑现？
  - 上一步产生的信息，下一步有没有用上？
  - 一路走下来，像不像**同一个产品**在跟我说话？
- 必须跨计划边界，不受"这是上个计划做的"限制
- 必须包含**没有任何操作时的第一眼状态**（空状态/首屏），不能只看操作后的状态

**规矩四：旅程审查不通过，不算完成。**
代码正确性审查（现有那套）继续保留 —— 它挡住的是 bug，确实有价值
（这次挡下了数据丢失和安全漏洞）。但它**不能替代**旅程审查。
两者都过，才算做完。

### 8.3 判定标准的差别

| | 代码审查 | 旅程审查 |
| --- | --- | --- |
| 单位 | 一个 diff | 一次完整客户旅程 |
| 问题形态 | 改错了 | 没接上 / 感觉不对 |
| 边界 | 本计划内 | 跨全部计划 |
| 证据 | 代码、测试 | 真实截图、走查记录 |
| 核心问题 | 这样写对不对？ | 客户走这一路，会不会觉得这是一个完整的产品？ |

## 九、风格系统重做：现在的三个风格"做了跟没做差不多"

founder 判断（2026-08-20）："我们目前的风格，我感觉太一样了，做出来跟没做的差别是不大的。"

### 9.1 量化验证：确实几乎一样

| | Ledger | Hearth | Blueprint |
| --- | --- | --- | --- |
| 背景 | `#f6f8fb` | `#f4f9f7` | `#f3f7fe` |
| 文字 | `#14273d` | `#153227` | `#0c182e` |
| 主色 | `#0570de` 蓝 | `#237570` 青 | `#2261dd` **也是蓝** |
| 字体 | 同一个 | 同一个 | 同一个 |
| 字重 | 500/600 | 500/600 | 500/600 |
| 字距 | 同一个 | 同一个 | 同一个 |
| 圆角 | **没有这个 token** | 没有 | 没有 |

三个背景肉眼分不出，Ledger 和 Blueprint 主色**都是蓝的**。
**这不是三种设计，是同一种设计的三个色调微调。**

### 9.2 根因：token 架构只有"颜色"一个轴

`ledger.css` 全部 token 盘点，除颜色外只有：`--border-strong/subtle`、`--hairline`、
`--font-sans/mono`（三个文件完全相同）、`--fw-medium/semibold`（相同）、
`--tracking-*`（相同）、`--dur`/`--ease`、`--shadow-hue`（只是个色相，不是阴影尺度）。

**没有间距/密度尺度、没有圆角尺度、没有字号尺度、没有真正的阴影尺度。**
架构上就只支持"换色"，不支持"换风格"——所以再怎么调也调不出差异。

### 9.3 行业设计实证（截了真实产品，不是看文章）

| 产品 | 行业 | 实际设计语言 |
| --- | --- | --- |
| **Procore** | 装修/承包商 | 等宽大写小标签 + **极粗黑体巨型标题**；近直角（2–4px）；**焦橙/铁锈**（工地安全色）；紧凑、重、硬边；气质：严肃耐用、"干活的工具" |
| **Fresha** | 美容/沙龙 | **圆润几何无衬线**；**全圆胶囊按钮**；**多彩粉彩编码**（粉/青/橙/蓝区分不同预约）＋紫粉渐变；**圆形真人头像**；疏朗留白；气质：亲切、以人为本 |
| **StoreHub** | 零售（**马来西亚本土**） | **暖米白背景**（不是冷白）；活力橙；胶囊按钮；真实硬件产品照 |

**关键结论：真正拉开差距的从来不是色相，而是这六个轴——**
1. **字体族**：等宽/超粗压缩 vs 圆润几何 vs 人文无衬线
2. **圆角尺度**：2px（工业）vs 8px（专业）vs 999px 胶囊（亲和）
3. **密度**：紧凑重型 vs 舒适 vs 疏朗留白
4. **主色角色**：单一高可见度警示色 vs 多彩语义编码 vs 温暖品牌色
5. **背景温度**：冷白 vs 暖米白 vs 有色调
6. **边框/阴影语言**：硬边平面 vs 柔和投影 vs 描边卡片

我们只动了第 4 项的色相，其余五项三个风格完全一致。**这就是"做了跟没做一样"的原因。**

### 9.4 StoreHub 额外收获：马来西亚本地信任信号

StoreHub 是马来西亚本土 POS 公司，直接面对 founder 的同一批客户。它首屏放的东西值得照抄：

- ⭐ **Google 评分**："4.7/5 rating out of 2,200+ Google reviews"（顶部第一行）
- 🇲🇾 **本地商家数**："Join 20,000+ Malaysian businesses"
- 🧾 **E-Invoice 合规徽章**（LHDN 强制，马来西亚商家的真实痛点）
- 💬 **WhatsApp 按钮与主 CTA 并列**（不是藏在角落）
- 暖色调而非科技冷蓝

我们现在这三样一个都没有。这些不是设计装饰，是**马来西亚中小商家的信任货币**。

### 9.5 风格系统重做的方向

1. **token 架构先补轴**：加入 radius、density/spacing、type-scale、shadow 四组尺度，
   风格才有得可调（现在架构上做不到）
2. **每个风格必须至少在 3 个轴上明显不同**，不能只差色相
3. **风格命名对齐数据库已有的 6 个行业推荐**
   （industrial / modern / warm-professional / professional / playful / minimal）
4. 起点从 21st.dev 主题库取色，但**字体/圆角/密度要按行业实证（9.3）自己定**

## 十、AI Agent 怎么调 prompt 才能输出稳定

founder 问："AI Agent 是要怎么调 prompt，输出变得稳定。"

### 10.1 现状盘点（我们已经做对了一半）

`app/api/analyze/route.ts` + `lib/openai/analysis-schema.ts`：

- ✅ 已用 **structured output**：`response_format: { type: "json_schema" }`，且 `strict: true`
- ✅ 已用 zod 二次校验，外面包了 try/catch
- ❌ **`enum` 用了 0 次** —— schema 只约束了**形状**，完全没约束**取值**
- ❌ `bottlenecks[].icon` 是 `strict` 必填、AI 每次都要编一个字符串，
  但渲染组件（`analysis-reveal.tsx`）只用了 `title` 和 `description`——
  **这个字段每次生成、每次丢弃**，纯浪费且是不稳定来源
- ❌ 校验失败只有 catch，**没有重试、没有确定性回退**

### 10.2 稳定性的第一原则

> **AI 的输出永远不应该决定"结构"，只能填"内容"。**

这样最坏情况下的失败模式是"**文案不够好**"，而不是"**页面坏了**"。
一个页面坏了的系统，客户直接流失；一句文案不够好，客户自己改一下就行——
而"客户自己改"本来就是这个产品的核心动作。

### 10.3 六条具体做法

**① 让 AI 选择，不要让 AI 生成（最大的杠杆）**

- ❌ "生成一个餐厅系统的布局" → 输出空间无限，必然不稳定
- ✅ "从这 8 个模板里选 1 个，从这 12 个模块里勾选需要的" → 有限集合，可穷举验证

这也是第四节选"模板 + AI 填充"而不是"AI 实时生成"的**第二个理由**：
不只是质量可控，更是**稳定性可控**。

**② schema 要约束取值，不只约束形状**

```ts
// 现在：AI 可以返回任何字符串
industry_style: z.string()
// 应该：只能是我们真实存在的风格
industry_style: z.enum(["industrial","modern","warm-professional",
                        "professional","playful","minimal"])
modules: z.array(z.enum(["customer","quotation","project","payment",
                         "booking","inventory","menu"])).min(1).max(6)
```

有限枚举 = AI 不可能返回我们处理不了的值。

**③ 把"结构决策"和"文案生成"拆成两次调用**

| | 结构决策 | 文案生成 |
| --- | --- | --- |
| 输出 | 选哪个模板、开哪些模块、用哪个风格 | 标题、说明、示例数据文字 |
| 形式 | 全 enum | 自由文本 |
| temperature | 低（要确定性） | 稍高（要自然） |
| 失败影响 | 严重（结构错） | 轻微（文案差） |

拆开之后，即使文案那次发挥不稳，**结构永远是对的**，页面不会坏。

**④ 验证 → 重试一次 → 确定性回退，三层都要有**

现在只有 try/catch（等于只有第一层）。应该：
schema 校验失败 → 用更严格的提示重试一次 → 仍失败则**回退到该行业的默认模板**。
客户永远看到一个能用的系统，而不是错误页。

**⑤ 删掉没人消费的字段**

`icon` 就是例子：`strict` 强制 AI 每次都要编，前端从来不用。
**每一个 AI 必须生成的字段都是一次犯错机会**——用不到就删掉。

**⑥ 给 2–3 个 few-shot 示例，而不是只描述规则**

B12 展示的 prompt 原文（见第六节竞品调研）之所以效果稳定，
是因为写得极其具体（精确到强调色、字体、构图），而不是"做一个专业的网站"。
**描述越具体，输出空间越小，越稳定。**

### 10.4 一句话总结

稳定性不是靠"把 prompt 写得更好"，而是靠**把 AI 能犯错的空间设计到最小**：
能用 enum 就不用自由文本，能选就不生成，结构和文案分开，
失败一定有确定性回退。
