# 客户 Portal + 拖拽编辑器 —— 已知问题记录

记录时间：2026-08-20
背景：客户账号系统 + 拖拽编辑器整个计划（Task 1-7 + 最终修复轮）代码层面已完成、审查通过、上线。但审查全程只检查了"代码对不对"（token 有没有硬编码、状态机逻辑对不对、RLS 权限对不对），**没有一次是"这个东西作为产品看起来/用起来怎么样"**。founder 亲自用真实账号登录看过实际画面后，指出问题很大。本文档记录这次真人视觉审查发现的问题，供下一个计划（编辑器视觉/体验重做）参考。

## 严重问题（按影响排序）

### 1. 编辑器空画布状态，全程从未被真正看过/验证过
所有测试和审查的流程都是"拖一个组件进去，看它显示对不对"——没有一次单纯打开编辑器、什么都不拖，看第一眼是什么样。但这恰恰是**每一个客户打开编辑器时最先看到的画面**：一个巨大的、纯色的蓝色虚线框，里面没有任何文字引导（比如"拖拽左侧组件到这里开始设计"）。对一个不懂技术的中小商家老板来说，这个画面很可能被理解成"页面坏了"，而不是"这里可以拖东西进来"。
- 文件：`design-system/editor/puck-config.tsx`、`design-system/editor/puck-theme.css`
- 需要确认：这是 Puck 的默认空状态样式，还是 token 换色过程中产生的非预期效果——从未被任何一轮审查截图确认过。

### 2. "Publish" 按钮语义是错的，不只是没翻译
这个按钮实际触发的是保存（付费客户存进数据库，免费客户弹出付费墙）——不是"发布"任何东西。写成英文 "Publish" 不只是本地化缺失，而是在告诉客户一件根本没发生的事。
- 文件：`app/[locale]/portal/[pageKey]/editor-client.tsx`（`onPublish={handleSaveClick}`，Puck 自带按钮文案无法通过 props 直接改，需要用 `overrides.header` 或类似接口整块替换）

### 3. 整个编辑器视觉上就是默认 Puck，只换了颜色，没有真正重新设计
工具栏布局、侧边栏、图标、组件列表卡片——全部是 Puck 自带的默认结构。之前几轮任务的"换皮"范围一直被限定为"把 Puck 的主题变量指向 Ledger 的 token 值"，从未真正重新设计这个工具该长什么样。而且 Ledger 自己的主色 `#0570de` 本身就是一个很普通的"SaaS 蓝"，跟 Puck 默认主题蓝几乎没区别，所以即使换色技术上正确，视觉上也没换出高级感。
- 文件：`design-system/editor/puck-theme.css`、`design-system/tokens/ledger.css`（`--color-primary: #0570de`）
- 需要用 Puck 更深的定制接口（`overrides.header`、`overrides.componentItem` 等）才能真正改变外观，不能只靠 CSS 变量。

### 4. 组件列表全英文、无图标，像开发者工具不像客户产品
`PageHeader`、`EmptyState`、`StatusDot`、`HeroCard`、`Avatar`——纯文字卡片，无图标，无中文名。目标客户是马来西亚中文中小商家老板，这个列表现在读起来完全是给程序员看的。
- 文件：`design-system/editor/puck-config.tsx`（组件的 `label` 目前用的是组件本身的英文名，Puck 的 `ComponentConfig`/字段都支持 `label` 覆盖，一直没用）

### 5. 登录页完全没有品牌感，跟目标客户的信任需求不匹配
一个纯黑网格背景，中间飘着一个没有 logo、没有任何视觉锚点的表单。这种"科技感/工程感"调性放在获客首页做差异化也许合适，但放在一个中小商家老板要反复登录、管理自己真实生意数据的地方，观感更像"黑客工具"，不像"可以信任的生意伙伴"。
- 文件：`app/[locale]/login/login-form.tsx`、`app/[locale]/signup/signup-form.tsx`

### 6. "客户自己设计系统"现在实际上是"客户自己设计一个页面"
5 个系统页面（dashboard / customers / quotations / projects / payments）里 4 个完全没有导航入口，只能手动改网址才能到达。核心卖点（客户自主设计整个系统）目前体验上根本感受不到——客户只会觉得自己在一个空白页面上拖了几个方块。
- 文件：`app/[locale]/portal/[pageKey]/editor-client.tsx`（`PAGE_LABELS` 只是静态文字，不是可点击导航）
- 这是最终全局审查已经发现的 Important 级别缺口（当时定为"先上线，做成后续任务"）。

### 7. 风格选择不可逆，但选择时完全看不到编辑器实际长相
选风格那一页（Ledger / Hearth / Blueprint）本身做得不错——用示例数据表格对比、界面也比编辑器精致很多。但客户是在"这个选择之后不能更改"的前提下，只凭一段文字描述 + 一张示例发票表格做决定，完全没有预览到选完之后编辑器实际是什么样子。等于是拿一个好看的东西，让客户对一个还没让他看到的东西做出不可撤销的承诺。
- 文件：`app/[locale]/portal/style-select/style-select-client.tsx`

### 8. 编辑器外壳（chrome）固定用 Ledger 风格，不随客户选的风格变化
客户选了 Hearth 或 Blueprint 之后，画布内容会应用对应风格，但编辑器自己的工具栏/侧边栏视觉上还是偏 Ledger 的浅色调——跟客户自己选的东西不完全一致，可能造成"我选的风格好像没生效"的困惑。
- 这是 Task 5 当时的明确设计决定（"外壳永远是 Ledger，不管客户选什么"），当时有它的理由（工具是 Formae 自己的，不是客户设计的一部分），但值得重新评估是否该继续这样。

## 之前全局审查已经记录、但还没处理的相关缺口
（跟上面视觉问题高度相关，适合一起排进下一个计划）
- 付费客户保存失败没有重试机制（spec 原本要求，计划阶段漏排了）
- 完全没有自动化测试保护 RLS 这道核心安全边界

## 建议
下一个计划应该把"让编辑器真正好看、好用、有品牌感"当作独立目标，不要再用"接上 token 变量"这种浅层换皮方式。需要：
1. 实际使用 Puck 的 `overrides` 接口重新设计工具栏、组件列表、空状态引导文案
2. 中文化所有客户可见文字（组件名、字段名、按钮文案）
3. 补上 4 个页面的导航入口
4. 重新设计登录/注册页面的品牌呈现
5. 每一轮审查除了检查代码正确性，必须包含真实截图 + 视觉走查这一环，不能只靠"拖一个组件测试通过"就算完成

## 竞品/参考产品调研（2026-08-20）

背景：founder 直接质问"有哪个成功的 AI SaaS 产品长得跟我们这样"，逼着做了一轮真实的竞品截图对比，而不是空谈。以下是发现和结论。

### 市场竞品：XYSTEM TECH SOLUTIONS
本地（KL·Cheras）传统定制开发团队，公开价格单：公司/个人网页 RM1,188 起、网页系统&后台 RM1,499 起、前端商城/网店 RM2,599 起、手机 App RM8,999 起。固定报价、分期付款（30/30/40）、真人本地团队。FB 帖子有 90 赞真实社交证明。
**结论：** 论价格、作品数、已有客户信任，现在赢不了。差异化必须靠"客户自己参与设计"这个市面上没人做的概念，不能打价格战。

### 通用设计标杆（Linear / Framer / Webflow）
共同点，也是我们现在最大的差距：
1. 界面是真正自己设计的，不是拿开源组件库换颜色
2. 到处都是真实图标，不是纯文字列表
3. 从不给用户看真正空白的页面——连"空状态"宣传图都是精心设计过的引导文案/插画
4. 有信任信号（客户 logo、真实数据示例、评分）
5. 有动效和细节反馈（发光、过渡、悬浮）

### 最接近我们业务模式的参考：B12.io
"Describe your idea. Launch in minutes." + AI 生成 + **真人团队**（设计+文案）二次打磨交付——跟我们"AI 分析 + 人工团队真正落地"的思路一致，只是他们做网站，我们做完整业务系统。

实际生成出来的系统模板截图非常有参考价值：
- **Studio Flow**（客户项目门户）：深藏青侧边栏 + 白色内容区，"Welcome back, Jane" 问候语，"5 个进行中项目 / 3 个待批准"数字卡片，项目卡片配真实图片 + 进度条
- **AssetFlow**（资产管理系统）：同样深色侧边栏+白色内容区，"Good morning, Ava" 问候语，数字统计卡片 + 柱状图 + 饼图 + 最近动态列表

**可直接借鉴的具体规律**（下次重做 dashboard 组件时的视觉目标）：
1. 深色/彩色侧边栏 + 白色主内容区的经典组合
2. 顶部一定有醒目的数字统计卡片，一眼看懂"这个系统在管理什么"
3. 真人称呼的问候语（"Welcome back, [名字]"），立刻让工具感觉"是我的系统"
4. 只用一个强调色贯穿全场（indigo/purple 或 navy），不是随便一个默认蓝
5. 真实数据可视化（图表、进度条、列表），不是空白占位
6. B12 展示的 AI 生成提示词原文非常具体（精确到强调色、字体、布局构图），说明好的输出需要给 AI 明确的视觉方向指令，不能只描述功能

### 最接近我们产品形态的参考：Durable.com
founder 亲自用自己的公司（Wei2Chee）注册体验过。侧边栏结构：Home / Website / SEO & GEO / Customers / Studio / Bookings / Agents（AI Partner / Blog / Website Leads / Google Reviews）——已经是一整套业务工具框架，跟我们 dashboard/customers/quotations/projects/payments 的思路很接近。

**值得直接照抄的细节：**
- 风格切换 UI：AI 生成后弹出"Here are some theme options"，几十个缩略图并排比较，客户看着实际效果选，而不是像我们现在这样凭文字描述做不可反悔的决定
- Publish 按钮在这里语义是对的（真的在发布网站）——反衬出我们编辑器里"Publish"按钮实际是"保存"，语义错误
- 侧边栏 icon+文字排列、Beta 标签、带倒计时的促销卡片

**核心业务模式区别（重要，不能搞混方向）：**
Durable 是纯 AI 自助——AI 生成完，客户自己编辑，编辑完**就是最终产品**，背后没有真人团队再做定制后端。它的 Customers/Bookings 等"系统"模块是所有客户共用的通用固定功能，客户没法设计这些页面长什么样，只是套上自己的品牌名。

**技术上"几十种风格一秒切换"是怎么做到的：** 内容（文字/图片）和"风格"完全分开存。系统预先做好一批"配色方案 × 排版模板"的组合（比如 6 种配色 × 5 种排版 = 30 种视觉效果），客户点一个缩略图，只是把同一份内容套进不同的 CSS 变量/排版组件，不用重新调 AI，纯前端切换所以秒开。**我们现在的 Ledger/Hearth/Blueprint token 架构本质上就是同一个思路**，加一层"实时预览 + 允许反悔"是可以做的，不需要推倒重来。

再进一步确认：Durable 那套"一秒换风格"的魔法，**只用在了 Website（营销落地页）模块上**，没有用在 Customers/Bookings 这些真正的系统功能上——每个客户的 CRM 界面长相都是 Durable 自己固定做好的。这再次证明"让客户自己设计真正的功能系统（不只是门面）"这件事市面上真的没人做，是真实的差异化。

### 两阶段路线图（founder 确认，任务周期长，分阶段推进）

**第一阶段（当前优先级，是产品能否成立的关键）：** 把"客户自己设计系统"这个核心概念做扎实——
- 真正的业务组件（报价单表格、客户列表、状态流转），不是现在这几个装饰性方块（PageHeader/EmptyState/Avatar）
- 每个业务组件要在 3 种风格（Ledger/Hearth/Blueprint）下都好看、都能用，尤其要保证状态标签、金额这些关键信息在任何配色下都清晰可辨
- 在这之上，才是"实时预览 + 允许反悔选风格"这类体验优化（顺序反了会变成"换肤功能很炫，但里面没有真正能用的系统"）

**Phase 1 具体起步方法（founder 确认，2026-08-20）：** 不从空白页面自己设计每个业务组件，而是两步走：
1. 从 shadcn/ui 免费的 dashboard 组件块生态（表格、统计卡片、状态标签、侧边栏——这个库本项目里已经在用，如 `components/ui/button`）里，挑选最接近报价单表格/客户列表/统计卡片需求的现成组件作为起点，而不是从零设计
2. 把这些组件的颜色变量，用 `design-system/editor/puck-theme.css` 已经验证成功的同一种做法（把外部库自己的语义 token 名对应到 Ledger/Hearth/Blueprint 的 token 名），对接进现有的三套风格系统

这样"设计得好不好看"这一半用现成专业组件直接解决，真正要做的工程只剩"换肤对接"，而且这件事在本项目里已经有成功先例（Puck 工具栏的换肤就是这么做的），不是从头摸索的新技术。

**第二阶段（未来扩展，不占用当前资源）：** 落地页构建器——
- 技术上不是另开一个产品，是同一个 Puck 编辑器**多注册一批营销类组件**（Hero 区块、客户见证、价格表、联系表单）
- 原材料很多已经现成：获客网站那个计划已经做出 `hero-section.tsx`、`ambient-backdrop`、Framer Motion 动效等素材，只是还没包装成 Puck 可拖拽组件
- 原因是 founder 未来业务上也可能接落地页类的客户需求（对标 XYSTEM 的"公司/个人网页"这条产品线），但落地页是市面上一堆模板工具都能做的commodity，不是差异化，所以明确排在第一阶段之后，避免两头做成半成品

## UI/UX 组件库研究（2026-08-20，founder 指出 research 做得不够后补做）

founder 的原话："我们还是没有做到很多 research 的工作，例如 21st.dev、motionsites、reactbits 这些网站，还有每个行业的风格。我们应该要怎么做出我们自己的 UI/UX 库出来，不能一上线什么都没有，至少要有真正的选择给到客户。"

`docs/design-references.md` 里这三个站一直标着 "Still unused" —— 这轮真正去查了。以下是**实测**结果，不是推测。

### 发现 1（最重要）：我们已经做好了 21 个组件，编辑器里只注册了 5 个

`design-system/components/` 下实际有 21 个组件，`puck-config.tsx` 只注册了 5 个（PageHeader / EmptyState / StatusDot / HeroCard / Avatar，全是装饰性的）。**16 个已完成的组件躺着没接进编辑器**：

| 未注册组件 | 是什么 | 为什么重要 |
| --- | --- | --- |
| `data-grid.tsx` (152行) | **真正的数据表格** | 这就是"报价单表格/客户列表"需要的东西，之前以为要从零做 |
| `rail-nav.tsx` (333行) | **侧边栏导航** | 这就是问题 #6"4个页面没有导航"的现成解法 |
| `filter-chips.tsx` | 筛选条件标签 | 表格配套 |
| `date-picker` / `month-picker` | 日期选择 | 报价单/账单必备 |
| `receipt-field.tsx` | 收据字段 | 直接对应 payments 页 |
| `combobox` / `text-autocomplete` / `listbox` | 输入控件 | 表单必备 |
| `modal` / `notification-toast` / `anchored-panel` | 弹窗/提示 | 交互反馈 |
| `columns-menu` / `confirm-submit-button` / `mobile-nav` / `rail-icons` | 配套件 | — |

**结论：Phase 1 的第一步不是"做新组件"，是"把已经做好的组件接进编辑器"。** 这部分几乎零设计工作量。

### 发现 2：数据库里的行业风格，和我们实际做的风格完全对不上

`industries` 表里 8 个行业各自推荐了风格，一共 **6 种命名**：

| 行业 | 数据库推荐风格 | 我们实际有的 |
| --- | --- | --- |
| 装修/承包商 | `industrial` | ❌ 没有 |
| 零售/门店 | `modern` | ❌ 没有 |
| 美容/沙龙 | `warm-professional` | ❌ 没有 |
| 教育/补习 | `warm-professional` | ❌ 没有 |
| 批发/分销 | `professional` | ❌ 没有 |
| 服务型公司 | `professional` | ❌ 没有 |
| 餐饮/F&B | `playful` | ❌ 没有 |
| 其他 | `minimal` | ❌ 没有 |

我们只做了 Ledger / Hearth / Blueprint 三种，**跟这 6 个名字一个都对不上**。也就是说：获客站的 AI 分析告诉客户"你适合 industrial 风格"，客户进到 portal 却只能在三个名字完全不同的风格里选。这是一个横跨两个子系统的断裂，之前没有任何一轮审查发现（因为每轮只看单个任务的 diff）。

### 发现 3：21st.dev 的主题库可以直接用，我们的代码已经"说同一种语言"

- 21st.dev 有 **Themes 专区**，几十个现成 shadcn 主题：Vercel / Modern Minimal / Zen Linen / Claude Amber / Sage Garden / Supabase / Elegant Luxury / Vintage Paper / Solar Dusk / Candyland / Neo Brutalism / Ocean Breeze / Nature / Graphite / **Amber Hearth** / Mint Signal / Kodama Grove / Cyberpunk / Mono …
- 每个主题**本质就是一组 CSS 变量**（`--background` / `--foreground` / `--primary` / `--card` / `--muted` / `--border` / `--ring` …）
- **关键实测**：我们 `app/globals.css` 里**已经有完整的这套标准变量名**，且 `components/ui/` 下已在用 shadcn 组件（badge / button / card / progress / textarea）。所以这些主题是**粘贴即用**，不需要改任何组件代码。

**这直接回答了"theme 转换怎样才不会很难"：不难，因为主题只是一组变量，而我们的地基已经是这套标准。** 从 3 种风格扩到 10+ 种，工作量是复制变量，不是重新设计组件。

### 发现 4：三个参考站各自的正确用途

| 站点 | 实测内容 | 用在哪 |
| --- | --- | --- |
| **21st.dev** | 12,000+ 组件 + 主题库。**每个组件都以 prompt 形式提供**，粘贴进 Claude Code 会"自动适配你的主题"。被 Google/Meta/Vercel/Shopify 等在用 | **Phase 1 主力**：主题库 + 补充业务组件 |
| **reactbits.dev** | 165+ 动画组件/背景，**永久免费**，开源。ColorBends / Aurora / Beams / Grainient 等，参数全可调 | **Phase 2**：落地页的动效和背景 |
| **motionsites.ai** | AI SaaS 网站设计画廊，每个作品可"Copy full prompt" | **Phase 2**：落地页整页设计参考 |

### 由此确定的 Phase 1 执行顺序（按性价比排序）

## 更正（2026-08-20，动手实现时发现）

开始实际注册组件时发现，"发现 1"里对 `data-grid.tsx` 的判断是错的：
**它不是一个表格组件，是一个"滚动视窗"包装器**——它接的是 `children: ReactNode`
（一整个 `<table>`），本身不提供 columns/rows 这种 Puck 能理解的 props。
"报价单表格已经做好了"这句话不成立，之前是看到 152 行代码没细看内部就下了结论。

实测后 16 个组件的真实分类：

- **可直接注册**（props 全是字符串/数字/数组，无 ReactNode）：
  `date-picker`、`month-picker`、`receipt-field`（FileUploadField）、
  `filter-chips`、`combobox`、`text-autocomplete`、`listbox`、
  `rail-nav`/`mobile-nav`（省略掉图标/自定义面板等可选的 ReactNode props，
  跟原来 HeroCard/EmptyState 的处理方式一样，是安全的子集不是错误）
- **不是画布内容，是程序控制的界面基建，不该进 Puck 组件面板**：
  `modal`、`anchored-panel`（靠 `open`/`onClose` 状态控制，不是拖上去的静态内容）、
  `notification-toast`（本身是通知队列系统）、`columns-menu`（要接真实表格状态）、
  `confirm-submit-button`（要在真实 `<form>` 里）、`field`（children 是 render-prop
  函数，技术上无法用 Puck 数据表达）
- **真正的"报价单表格"这类东西，需要新建**：用 `data-grid.tsx` 当滚动容器 +
  自己的 `<table>`/`StatusDot` 组装成一个真正 Puck 友好的表格组件——
  这是 Phase 1 真正的核心工作量，不是"已经做好躺在那"。

## 2026-08-20 视觉重做（founder 反馈："system 内部真的做到很丑"、"landing pages 还没做到成品的样子"）

上一轮结案记录说"已解决"的那批，是**功能层面**的（页面能到、组件是中文、AI 分析有接上）。
founder 打开来看，说的是**观感**——两件事，都成立。用浏览器实测过，不是靠印象判断。

### 系统内部：实际量出来的问题

| 问题 | 实测数字 |
| --- | --- |
| 右侧属性面板常驻但空着 | 1440px 视窗里固定占 290px，没选中东西时只显示一个「整个页面」标题 |
| 每一页的表格「状态」栏被切掉一半 | 画布 792px − 侧边栏 220px = 524px，`RecordTable` 自己 `min-w-[520px]`，超出 21px |
| 侧边栏是白底纯文字 | 无图标、无品牌块、active 只靠一点浅灰底色 |
| 侧边栏高度只有内容那么高 | 900px 的页面里，深色栏在 387px 就断掉 |
| 顶部工具条堆了四行 | 180px，其中一整行只是重复显示当前页名（页面 tab 上已经高亮着） |
| 组件面板缩略图看不见 | 全画在 `--color-ink-800`(#e4e9f0) 上，底是 `--color-ink-900`(#ffffff)，对比度 1.11:1 |
| 侧边栏品牌名是注册邮箱前缀 | `tianyou.demo`，同时出现在系统名和账号位 |
| 总览页只有一个孤零零的数字 | `HeroCard` 早就支持 3 个副指标 + 走势线，Puck 注册时只暴露了 label/value/href |
| 在总览页，三个导航项同时高亮 | 通知/账号设置的 href 都指向 dashboard，`pathname ===` 判断三个都命中 |

### 做了什么

1. **三套 token 各自加一组 `--color-nav-*`（深色导航底）** — 这是 `docs` 里 B12/Durable 调研早就写下的第一条结论（"深色侧边栏 + 白色主内容区"），一直没做。底色直接用每套自己的 `--color-paper`，所以 Ledger 是藏青、Hearth 是墨绿、Blueprint 是深蓝，三套一眼分得出。每一对颜色都用 WCAG 公式算过写在注释里；accent 是各自 `--color-primary` 提亮（原色在深底上只有 2.5–3.2:1，不够）。
2. **属性面板改成跟着选中状态开关** — 没选东西就收起来。画布 792 → 1082px，表格切边问题跟着消失。**这个 bug 的成因是一块空面板。**
3. **`RailItem` 加 `iconName`（字符串）** — Puck 的 field data 是 JSON，装不下 ReactNode，所以生成的导航一直是纯文字。`RAIL_ICONS` 用页面 key 当键，模板直接传 key，对不上就退化成纯文字。
4. **深色底画在 `SystemShell` 的外层（会被拉伸的那个盒子）**，不是只画在 `<aside>` 上 — Puck 在中间插了两层 `height:auto` 的 wrapper，百分比高度传不下去。把那两层改成 flex 能修好高度链，但也会改动 Puck 定位拖拽占位符的盒子——为了一个颜色问题去动它不划算。
5. **`HeroCard` 补上 `stats`/`spark`/`chgSuffix`** — 顺带说明：B12 的模板是一排四个等大数字卡，**没有照抄**。`hero-card.tsx` 自己的注释引 NN/g 反对这种排法（四个一样大 = 四件事一样重要 = 读的人得自己找重点）。保留组件自己的主张：一个大数字 + 三个副指标。
6. 工具条四行并三行、缩略图提高对比、品牌名换成按行业的占位（「我的装修公司」而不是编造一个假公司名）、通知/账号设置指向 `#`。

### Landing page：原来只有两屏

实测 `document.body.scrollHeight = 1775`。一个没点行业的访客，看到的就是 Hero + 八个行业列表，然后文档结束——没有说明产品是什么、没有价格、没有"跟找网页公司做有什么不同"的回答、没有 footer。
后面那些（同行案例 / 分析 / CTA）**全部要先选行业才会渲染**。

补了四个 section + footer：PROCESS（三步）、SCOPE（你拿到什么）、PRICE（RM 5,000 + RM 100–300/月，直接写在页面上）、QUESTIONS（5 条），中英文都写了。现在 4655px。

**这四个 section 没有编号。** `SectionShell` 的 `index` 改成可选：编号是"访客流程的第几步"，而流程里有三步要先选行业才存在——给参考性内容编号，等于对没选行业的人显示 01、06、07。

### 验证

浏览器实测，不是靠 review：5 个页面全部无切边（表格右缘 1391 < 画布 1416）、7 个图标、三套风格导航底色分别是 rgb(20,39,61)/rgb(21,50,39)/rgb(12,24,46)、拖拽仍然正常（表格 1→2）、拖完属性面板会自己回来、/en 无缺失翻译键、console 零报错。69 个测试通过（含 token 同步测试，所以新 token 确实进了 scoped copy）。

### 这一轮没做的

- 风格名在工具栏仍是 Ledger / Hearth / Blueprint 三个英文词。选风格那一页有完整中文说明，工具栏只有名字。**故意没改**：改成中文短名会跟选择页对不上，制造一个比现状更糟的不一致。要改就两边一起改，是独立的一件事。
- 侧边栏底部的通知/账号设置仍然贴着导航项，没有真的沉到底 —— `<aside>` 撑不满高度（原因见第 4 点）。深色底补上之后视觉上看不出来，但结构上还是没修。

## 2026-08-20 第三轮（founder："哪里有人一来就直接进设计的？还有语言也不给人家去切换"）

上一轮修的是**观感**，这一轮 founder 指出的是**结构**，两条都成立，而且比上一轮更根本。

### 问题 1：登录后直接掉进编辑器

`app/[locale]/portal/page.tsx` 之前没有任何 UI —— 读一下 `projects.style` 就 `redirect("/portal/dashboard")`，
而 `/portal/dashboard` **就是 Puck 编辑器**。所以一个装修老板登录后看到的第一个画面，
是一个左边挂着组件面板的拖拽画布。

**没有任何产品拿创作工具当门面。** 去翻了两个参考产品的实际结构：

- **Durable**：登录进的是 Home —— 问候语、你的网站、各个模块、下一步动作。
  编辑器是你从 Home 里*选择*进入的一个目的地，不是落地页。
- **21st.dev**：进去是一个 gallery —— 左边深色侧栏带分类和数量（Backgrounds 365、
  Heroes 1152…），主区域是一排排**大张视觉预览卡**，你先浏览再动手。

两个都不是一进去就给你一张画布。

**做法：** `/portal` 变成真正的首页（Durable 的结构 + 21st.dev 的画廊呈现）：
问候 + AI 对这门生意的那句总结 → **五个页面的画廊，每张卡片是那一页真实的缩小渲染** →
风格卡片（照 21st.dev Themes 那一套：色板圆点 + 该风格自己的底色面板 + 名字设在面板里面）
→ 接下来（需求书 / 交给我们建）。编辑器加了「← 我的系统」返回入口，
style-select 选完之后也改成回首页而不是进编辑器。

**为什么卡片是真渲染不是示意图：** 跟 `design-system/editor/component-preview.tsx`
的判断正好相反，而且是同一条理由决定的两边。那个文件预览的是**组件**，
显示在编辑器自己的 Ledger 外壳里 —— 给选了 Hearth 的客户看 Ledger 版本的组件，
是一个会骗人的预览，所以画示意图。这个文件预览的是**客户自己的页面**，
而且就在客户自己的风格 scope 里 —— 给一页他已经改过的东西画示意图，
等于用一个更差的复制品替掉真东西。21st.dev 的画廊做对的就是这一点。

### 问题 2：整个 app 没有语言切换

`i18n/routing.ts` 有 zh/en，每一个字符串都在 `messages/{zh,en}.json` 里，
`/en` 从头到尾渲染正常 —— **就是没有任何一个控件能到达它**。
英文那一半是做好的、付了成本的、然后完全够不着。这比没做更糟。

在这个市场上尤其要紧：马来西亚一间公司常常是老板看中文、员工看英文，
而且你去 demo 的时候，坐在对面的那个人不一定读中文。

`components/locale-switcher.tsx` 现在挂在 Hero 图头、登录/注册、portal 首页、编辑器工具条。
每个颜色都带字面 fallback —— 这个控件同时挂在 portal 的 `.ledger/.hearth/.blueprint` scope
（有 `--color-nav-*`）和获客站的 `app/globals.css`（没有），
少了 fallback 的话，`color` 会停在继承值，在深色 Hero 上就是黑字黑底。

### 顺手修的：登录/注册页（本文档问题 5，一直挂着）

之前是 `max-w-sm` 一个标题加一个表单，浮在深色网格上，没有品牌、没有说明、没有语言切换。
现在有 `components/auth-shell.tsx`：品牌标、语言切换、卡片、一句说明。
刻意做得克制 —— 不是重新设计，是补上"这个 URL 后面有一家公司"这个信号。

### 浏览器实测抓到两个真 bug（review 抓不到的）

1. **`<a>` 套 `<a>`。** 卡片本来是 `<Link>` 包住整张卡，而卡里的真渲染带着侧边栏
   自己的五个 `<a>`。Playwright 点击时解析到 **6 个** 匹配元素，控制台是 hydration 报错。
   改成 footer 里一个 `<Link>` + `after:absolute after:inset-0` 拉伸覆盖整卡 —— 
   一个链接、一个可读名称、整卡可点、没有嵌套。
2. **`aria-hidden` 反而更糟。** 预览里那些链接对读屏器隐藏了，但**还在 tab 顺序里**，
   焦点会停在读不出名字的控件上；`pointer-events-none` 只挡鼠标不挡键盘。
   改用 `inert` —— 只有它同时从命中测试、tab 顺序和无障碍树里移除整个子树。

另外量出来：`Render` 模式下 SystemShell 的 `min-h-full` 又断了（720px 舞台上只有 387px），
所以每张卡片的深色侧栏都只到三分之一处，下面一片白。这里链路短（`Render` 只插一层 wrapper，
编辑器插好几层），所以是真修好的：`[&>*]:h-full`。

### 验证

登录后落在 `/zh/portal`（不是编辑器）；5 张卡片、5 个预览全部完成缩放；
中文↔EN 切换在 portal 内往返正常且英文文案齐全；卡片 → 编辑器 → 返回首页往返正常；
console 零报错；69 个测试通过。

### 仍未解决

- 风格名还是 Ledger / Hearth / Blueprint 三个英文词（首页卡片下面补了中文说明「紧凑·表格多、行数多」等，
  但名字本身没改，理由同上一轮：要改就跟 style-select 页一起改）。
- 只有 zh / en，没有马来文 —— `messages/` 里没有 ms.json，加语言是加一份翻译，不是改架构。

## 2026-08-20 第四轮（founder："还没完全是一个成熟的 AI SaaS"，桌面优先，手机延后）

先做了一次三个视窗的完整清点（`scratchpad/audit.py`），不再凭印象。结果分两类：

**手机（founder 明确说延后，记录在案不做）**
- 编辑器在 390px 下横向溢出到 608px，工具条右半截在屏幕外
- 组件面板在手机上根本不渲染（`paletteVisible: false`）→ 手机上加不了任何东西
- 平板 820px 下画布只有 502px，表格又被切
- 触控目标普遍小于 32px（语言切换 38×24、登出 26×20、卡片链接 68×20）

**桌面（这一轮做的）**

### 1. 没有任何社交元数据 —— 链接发出去是一条灰色 URL

实测 `meta` 全空：没有 description、没有 og:*、没有 twitter card、没有 og:image、没有 apple-touch-icon。
founder 的分发路径就是**把链接发到 WhatsApp**，而预览卡就是点开之前那两秒的全部说服力。
这是分发 bug，不是润色项。

补了完整 metadata + `app/[locale]/opengraph-image.tsx`（`ImageResponse` 生成，中英各一版）。
**难点是字体**：Satori 不带 CJK 字形，中文标题会渲染成一排豆腐块，比没有卡片更糟；
完整 Noto Sans SC 是几 MB，不可能塞进边缘渲染。解法是 Google Fonts 的 `text=` 参数
（只返回用到的那几个字，几 KB），并且**故意用一个很旧的 User-Agent** —— Google 对现代
客户端返回 WOFF2，而 Satori 读不了 WOFF2。

### 2. 数据库里从来没有「公司名称」这个东西

`migration 20260820180000`。之前每一套生成的系统都在用手边能拿到的东西当名字：
先是注册邮箱前缀（`tianyou.demo`），后来是按行业的占位（`我的装修公司`）。
这个名字出现在**每一页的侧边栏、首页、需求书、和交接的 WhatsApp 对话里**。
一套说不出老板公司名字的系统，做得再好也是 demo。

加了 `projects.business_name` / `owner_name` + `update_business_identity()` RPC（security definer，
无 id 参数，和 `update_project_style` 同一个形状），首页加了设置对话框。

**改 `get_my_business_context()` 时差点造成静默回归**：第一版重写漏掉了原来的
`lateral` join（取**最新**一条 analysis_results —— 客户重填问卷会累积多条，普通 join 会变成
任取一条），也漏掉了 `language` / `before_workflow` / `style_recommendation`。
读了原始 migration 才发现。已在新 migration 的注释里逐条标明必须保留的原因。

### 3. AI 只是一个输入框 —— 这是「AI SaaS」最大的缺口

之前：工具条上一个 field，一行回复，下一次请求就把它冲掉。对一个卖点是
「不懂电脑的老板用讲的就能改系统」的产品来说，这是**功能写了但没做**。三件事都缺：

- **不记得自己做过什么**：回复会消失，客户没法回头看改了什么
- **不知道该说什么**：给一个空输入框，等于把「空白画布」问题换了个地方再犯一次
- **没法只撤销某一次**：全局 undo 会把之后的拖拽一起退掉

现在是 `ai-assistant.tsx`：完整对话记录、每一轮标注「改了 N 处」和没能改的原因、
空状态给三条真实的建议问法、**每一轮自带修改前的快照**所以能单独撤销那一次。

用 Puck 的 `puck` override（包住整个编辑器布局）而不是 `fields` override 或 fixed 覆盖层 ——
只有它能让面板成为画布的**兄弟节点**，画布真的变窄（实测 1082 → 782）而不是被盖住。

**对话状态提升到 `editor-client`**：Puck 会随编辑器 re-render 重建 `overrides` 里的渲染函数，
而助手自己成功改一次就会触发 re-render —— 状态放在组件里会被它自己的结果清空。

### 4. 保存状态

之前只有一个按钮，客户问「刚才存进去了吗」只能再按一次。
现在：`Ctrl/⌘+S`、「还没保存 / 已保存」指示、以及只在有未保存改动时才挂上的
`beforeunload` 拦截（免费用户没有服务器副本，只有本地草稿，所以这是最后一道）。

### 5. 表格宽度预算（面板一开，切边就回来了）

助手面板打开后画布 782 → 减侧边栏 228 → 减 shell padding 48 = 表格只有 458px，
而 `RecordTable` 的 `min-w` 是 520 —— 状态列又被切一半。
这是**同一个 bug 第二次出现**：上一轮靠「把画布变宽」修的，任何一个面板打开就会复发。
改成 440（四列在 440 仍然可读），并把 `DataGrid` 的边缘阴影从 0.2 加深到 0.34 ——
画布被压窄时，那道阴影是唯一告诉客户「表格还有内容在右边」而不是「坏了」的信号。

### 验证

设置保存后刷新仍在、侧边栏和账号位都换成真名；助手面板让画布 1082→782；
对话记录留住问题和「改了 1 处」；单轮撤销生效且画布还原；三个页面在面板开/关两种状态
下都不切边（表格右缘 1091 vs 画布 1116）；console 零报错；69 个测试通过。

### 这一轮没做的（明确列出，不含糊）

- **命令面板（⌘K）** —— 成熟工具的标配，还没做
- **加页面 / 删页面** —— 页面集合仍然由行业固定，客户不能自己加一个「员工排班」
- **通知、账号设置** —— 侧边栏里那两项仍然指向 `#`，是系统预览的一部分，不是能用的功能
- **版本历史 / 自动保存** —— 只有手动保存和当前会话的 undo
- **手机和平板** —— 见上面清点，founder 已确认延后

## 2026-08-20 第五轮：客户可以自己加/删页面 + AI agent 的真实能力

### 先回答 founder 的问题：AI agent 做好了吗？没有。

实测三条请求，把它做不到的事情钉死（不是推测，是跑出来的回答）：

| 客户说 | AI 的回答 | 结果 |
| --- | --- | --- |
| 表格加一列「负责的师傅」 | 「现有操作不支持为表格新增列。」 | 栏位没变 |
| 帮我加一个「员工排班」的页面 | 「现有操作无法新增独立页面。」 | 没加 |
| 把报价单那一页删掉 | 「当前页面列表中没有报价单页面，无法删除。」 | 没删 |

**它现在能做的**（5 个操作，全部限在当前这一页内）：改任何文字（含栏位标题）、
加/删一个组件、加一行示例数据、改流程步骤。

**而且我自己埋了一个坑**：空状态里三条建议问法之一就是「表格加一列「负责的师傅」」——
客户点开 AI 面板第一件事就是点建议，而这条**必定失败**。等于第一印象就是「这功能坏的」。
已换成它真的做得到的（改流程）。

### 这一轮做的：页面归客户

`migration 20260820200000`。之前页面集合完全由行业决定（`pages_for_industry()`），
装修的拿五页，加不了第六页也删不掉一页。**客户真正能设计的只是别人选好的那套页面的内容**，
比落地页上写的那句承诺小一圈。

- `project_pages.title` — 客户自己给页面起的名字
- `page_key` 的 check 从「七个字面量」放宽成「七个字面量 **或** `custom_[a-z0-9]{8,32}`」
- `add_project_page(requested_key, new_title)` / `remove_project_page(target_key)`
  两个 security definer RPC，无 id 参数，从 `auth.uid()` 解析自己的项目

**两种页面，一张表。** 可以加一个我们已经会做的类型（带真实示例数据和行业词汇），
也可以起一个我们从没听过的名字（「员工排班」「材料库存」）。第二种才是「设计」而不是「点菜」，
所以它是对话框的默认输入，现成类型放在下面当快捷方式。

**custom key 是随机 hex 不是标题的 slug**：标题可以改、可以重名（两个「收款」），
而 key 是所有 layout、路由、保存调用寻址用的东西——从标题推导会让改名要么弄坏路由要么撞车。

**dashboard 不可删**：每一页的侧边栏都链回它，`/portal` 也送人去那里。
数据库层面就拒绝，UI 只是配合这条规则，不是这条规则本身。

**页面上限 12**：侧边栏是固定宽度的一列，需求书是给人读的。四十页不是谁设计出来的系统，
是循环没停或者按钮卡住了。

### 为什么加页面故意不走 AI

`/api/portal/edit` 明确不落库（见该文件注释）——这条边界是付费门槛还有效的原因，
也是任何 AI 修改都能用跟拖拽同一个按钮撤销的原因。加页面是一次数据库写入，
硬塞进助手要么破坏这个契约，要么把一次未付费的写入藏在聊天框后面。
所以助手改成**告诉客户去哪做**（首页的「加一页」），这比在错的地方做掉更好。
Durable 也是这个分工：模块从导航加，内容用 AI 改。

### 类型层面的代价，说清楚

`PageKey` 原本是七个字面量的联合类型，贯穿模板、spec、三个 server page。
custom 页面必须打破它，所以引入了 `PageId = string` 和 `PageRef = {key, title}`，
`sortPages()` 处理混合排序（内建页按设计顺序在前，客户自己加的按添加顺序在后——
内建那一段是有设计的阅读顺序，按创建时间插进中间会破坏客户没选择过的顺序）。

**编辑器的页签标签不能再在客户端查 i18n**：客户自己加的页面没有
`portal.editor.pages.*` 这条消息，而 next-intl 缺 key 是抛错不是回退。
标签改成在 server 上用 `pageLabel()` 解析好再传下来。

`get_my_business_context()` 的调用从「只在需要生成页面时」提到「每次都调」——
页签现在要带行业词汇和客户自己的标题。

### 验证：用这个功能修好了它自己造成的破坏

跑测试时我的选择器点错了按钮，**真的把 demo 账号的「客户」页删掉了**。
然后就是用刚做的「加一页 → 客户」把它加回来的，再把测试加的「员工排班」删掉，
demo 账号回到承包商标准的五页。add 和 remove 双向都在真实数据上验证过了。

**教训（下次写浏览器测试必须记住）**：首页上有**五份完整的 app 副本**（页面预览），
所以任何通用选择器都会匹配到预览内部读到错的元素。连着两次读出假结果
（一次说 transcript 是空的，一次说每张卡都链到 dashboard）。
**这一页上的每个选择器都必须排除 `[inert]` 子树。**
